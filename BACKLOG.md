# Backlog

Known issues and planned improvements that aren't scheduled yet. One section per item: **Problem** (what broke and where it was seen), **Fix** (the intended approach and its open questions), plus the tests and docs it touches. When an item ships, delete it here and record it in `CHANGELOG.md`.

## 1. Codemod under TypeScript 7

**Problem.** `--fix` drives the consumer's `typescript` language service in `codemod-worker.js`, and TypeScript 7 (the native port) ships no JS compiler API. Since the fix for this, the daemon detects TS ≥ 7 and reports `--fix` as unavailable with that reason, so a TS 7 project (`afsp_profit_loss`) gets typechecking but no assisted fixes.

**Fix.** Drive TS 7's `typescript/unstable/sync` API. It has symbols and per-file references (`getSymbolAtPosition`, `getReferencesToSymbolInFile`, `getReferencedSymbolsForNode`) but no `findRenameLocations`, and it reads files from disk, while the worker serves the *previous* generated file as an in-memory overlay (see `unstable/fs` for a virtual filesystem). Wait until the API stops being `unstable`, or accept rewriting the worker against it. Alternative: let a consumer point `--fix` at a `typescript@5` installed alongside under an alias. Tests: the existing codemod suite, run against the TS 7 backend. Docs: `docs/typecheck-and-fixes.md`.

## 2. `@airgen/ui` utilities lose to the consumer's Tailwind

**Problem.** The package ships precompiled, unprefixed Tailwind utilities (`dist/styles.css`), and the interface scaffold runs its own Tailwind over `frontend/`. Any class both sides emit is defined twice at equal specificity, and the consumer's copy loads later, so it wins. Dark variants are the visible casualty: `Text variant="title"` is `text-neutral-900 dark:text-gray-100`, and once the extension also uses `text-neutral-900` the plain rule overrides the package's `@media (prefers-color-scheme: dark)` rule, leaving black text on a dark frame. `RecordTable`'s header stayed `bg-neutral-50` the same way. Seen in `sandbox/` (the airgen tester) on 2026-10-18, fixed there only by moving the tester's own classes onto the scaffold's `gray-grayNNN` tokens. A consumer has no reason to avoid `neutral-*`.

**Fix.** Prefix the package's utilities (Tailwind's `prefix: 'ag-'`, rewriting every class in `src/`) so the two sets can't share a selector. Scoping with `important: '.airgen-ui'` also raises specificity, but it needs a wrapper element around every portal (Select menu, Popover, Dialog, Toast) and still loses to a consumer `!important`. Native `@layer` is the wrong tool: layered rules lose to the consumer's unlayered ones. Open question: whether the prefix leaks into the public API (`className` props and `optionClassName` stay consumer classes, so it shouldn't). Tests: a `dist` CSS test asserting every utility selector carries the prefix, and a jsdom test rendering `Text` beside a consumer stylesheet that defines the unprefixed class. Docs: `packages/ui/README.md` (styling section).

## 3. `@airgen/ui` dark mode follows the OS, not Airtable

**Problem.** `packages/ui/tailwind.config.cjs` sets `darkMode: "media"`, so the components switch on the iframe's `prefers-color-scheme`. Airtable doesn't paint the extension frame: with no background of its own the tester rendered on white while `prefers-color-scheme` reported dark, so every `dark:` variant fired (light text, dark chips) on a white page. The scaffold sidesteps this by painting `bg-gray-gray50 dark:bg-gray-gray800` itself. It's unverified whether Airtable sets the frame's color scheme from its own theme or whether this is just the OS setting. If it's the OS, a user with a dark OS and Airtable in light mode (or the reverse) gets the wrong palette.

**Fix.** All three SDK flavors export `useColorScheme(): {colorScheme: 'light' | 'dark'}` (`shared/ui/use_color_scheme.d.ts`), which reports Airtable's theme. Switch to `darkMode: ['selector', '[data-ag-theme="dark"] &']` (with item 2's prefix) and add an SDK-free `ThemeProvider colorScheme={…}` in the root entry that sets the attribute on its own element and on every portal container. The Phase 4 per-flavor entries bind it to `useColorScheme` so consumers get it for free. Keep a `colorScheme="system"` mode that falls back to the media query. Open question: whether components should paint their own surfaces (`Table`, `Popover` already do) or leave the page background to the consumer, as the scaffold does. First verify in the sandbox, with Airtable and the OS set to different themes, what `useColorScheme` and the media query each report. Tests: a provider test that toggling `colorScheme` flips a `dark:` class on a portalled `Select` menu. Docs: `packages/ui/README.md`.

## 4. `SchemaObserver` panel is unreadable in dark mode

**Problem.** The observer renders plain DOM with fixed light-theme colors (it can't use the SDK component library, see the CLAUDE.md invariant). In the dark interface the "Copy schema" button is nearly invisible against the frame. Seen in `sandbox/` on 2026-10-18.

**Fix.** Add an optional `useColorScheme` to `BlocksSdkAdapter` (`sdk.ts`), bound in `index.ts`, `interface.ts` and `base.ts` (all three SDKs export it), and pick the panel's palette from it, defaulting to light when the adapter lacks it. That keeps `SchemaObserver.tsx` SDK-free. Tests: `entries.test.js` already pins the imports; add an observer render test with a fake adapter reporting `dark`.
